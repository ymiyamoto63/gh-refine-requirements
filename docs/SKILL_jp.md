# refine-requirements

事業責任者が書いた粗い要件 — 典型的には不完全・曖昧でビジネス用語で書かれている — を受け取り、設計者が推測に頼らず設計フェーズへ渡せるほど精緻な要件定義書に変換する。まずリポジトリを調査し、次にユーザーへ選択式で質問し、最後に文書を作成する、という手順で行う。

解決策の設計やコードの記述は行わない。成果物は要件定義書のみ。

## 入力

粗い要件はチャットのテキスト、またはファイルへのパス(.md / .txt — 読み込むこと)として渡される。どちらもない場合は、作業を始める前に要件を尋ねること。入力に複数の独立した機能が混在している場合はその旨を指摘し、機能ごとに1文書ずつ分割することを提案する(出力の慣例は1機能1ファイル)。インタビューを始める前にユーザーに選んでもらうこと。

## ステップ1 — 質問する前に調査する

自分で答えられる質問は絶対に尋ねない。インタビューの前に、対象プロジェクト(特に指定がなければカレントディレクトリ)を調査する。

- `README`、`docs/`(特に `docs/pipeline-config.md` と、既存の `docs/requirements/*.md` があれば)から、規約や過去の意思決定を確認する。
- 機能が触れるコード領域: 類似の既存機能、画面・ルーティング構造、APIパターン、データモデル。これが後の推奨事項の根拠になる。

調査は機能に見合った規模に留める: ファイル全体を読むより絞り込み検索(Glob/Grep)を優先し、ファイルを通読するのは機能が直接触れる箇所に限る。推奨の根拠を示せる状態になった時点で調査は完了 — リポジトリ全体の理解が目的ではない。読み取り専用の探索サブエージェント(Explore など)が使える環境では、調査を委譲して要約だけをコンテキストに残すのが良いトレードになる。

この調査で解決できることはすべて解決する。残ったものがインタビューの材料になる。調査から解決した曖昧点は、質問する*代わりに*解決したものとして記録しておく — これらはユーザーの意思決定ではなく推論なので、制約セクションの前提リストに入れ、ユーザーが文書レビュー時に誤った推測を否認できるようにする。

## ステップ2 — インタビューのループ

一度のパスで、作られるものを実質的に左右するすべての曖昧点を洗い出す — 機能面のパスとその後の非機能面のチェックに分けないこと。非機能面の発見(例: コンプライアンスやデータの機微性に関する懸念)が後から出てくると、すでに一括で質問した機能面の判断を覆しかねないため。リストには2種類の項目が混在する。

- **機能面の曖昧点**(主題): 挙動、画面、データ、エッジケース、権限としての振る舞い。
- **非機能面の曖昧点。ただし仕様を実質的に左右し得るものに限る**: 認証・認可モデル、個人情報や機微データの扱い、設計を左右する規模のデータ量・パフォーマンス、外部連携の可用性、法務・コンプライアンス上の制約。ありきたりな非機能要件(一般的な性能要望、ロギングの慣例)はリストに含めない。

洗い出しの際は、以下のカバレッジチェックリストを確認する — これらは要件定義でありがちな見落としである。

- アクターと権限: 誰が使うか、ロールによって挙動が変わるか
- 異常系・エッジケース: 入力不正 / 0件 / 上限超過 / 外部サービス障害時の挙動
- データ: 入出力の形式、保持期間、**既存データの移行の要否**
- スコープ境界: メモに書かれていないが隣接する機能を、やるのか・やらないのか
- 同時実行・競合、通知・監査ログの要否

このチェックリストが統制するのは*洗い出しのみ*であり、それを質問にするかどうかは以下のインパクト順序と予算に従う。この機能に明らかに無関係な項目は単純にスキップする。

結合したリストはインパクト順に並べる — 仕様を大きく左右する回答を持つ質問を先に — 予算を最も重要な箇所に使うため。

**予算: 合計30問 — ハードキャップであり、目標ではない。** 典型的なメモは3〜4ラウンド・8〜15問で収束する。30問に近づいてよいのは本当に大きな機能だけ。各ラウンドの質問を提示する*前に*、その時点までの累計数を明示する(例: `質問 5–8 / 30`)。最終まとめだけでなく毎回示すこと。実質的な曖昧点が残っていなければ、その時点で早期に打ち切る — 上限に向けて水増ししない。予算が尽きた時点で残っている項目はすべて未決定事項になる(ステップ3参照)。

質問は1ラウンドあたり最大4問の関連する質問をまとめて提示し、往復回数を減らす。各質問は以下を満たす。

- 2〜4個の具体的な選択肢。可能な限り互いに排他的にする。
- 推奨する選択肢には「（推奨）」と一行の根拠を付ける。推奨の根拠は必ず次のいずれかに紐付ける: **明示されたビジネス上の目的**(メモの背景・目的に最も資するもの)、**UI/UX**(エンドユーザーにとって最も違和感がないもの)、**実装難易度**(構築が最も安価・安全なもの)、**リポジトリの現行設計**(ステップ1の調査で見つかった既存パターンに合致するもの)。どれに基づくかを明示する。根拠が現行設計の場合は、見つけた具体的なファイルやディレクトリ(例: `src/features/export/`)を引用し、主張を検証可能にする。根拠付けできない推奨には「推奨」を付けない — 根拠のない推奨は、推奨なしより悪い。
- 環境に `AskUserQuestion` ツールがあれば使用する(推奨の選択肢を先頭に、「（推奨）」と表示)。それ以外(例: GitHub Copilot)の場合は、選択肢を番号付きリストとしてチャットに提示し、回答を待ってから続行する。選択肢にない自由記述の回答は常に有効であり、そのまま取り込む。

予算の数え方: ユーザーに実際に提示したすべての選択式質問がカウント対象であり、ある回答によって派生するフォローアップ質問も含む。入力メモを尋ねること、機能分割を提案すること、ファイル名を確認することはカウントしない。ある回答が粗いメモや以前の回答と矛盾する場合は、その矛盾を指摘し、どちらを優先するか確認してから取り込む(この確認もカウント対象)— 矛盾を黙って取り込むと文書全体の信頼性が損なわれる。

回答はその場で記録する: 各ラウンドが終わるたび、次のラウンドを提示する前に、回答1件につき決定記録1行を出力ファイル(ステップ4のパス — スラッグは最初のラウンドで確定する。この機能の文書が既に存在していた場合は更新モード〔ステップ4参照〕であり、そのファイルに追記する)へ追記する。長いインタビューはコンテキストウィンドウより長生きし得る — 恒久的な記録は会話の記憶ではなくファイルであり、ステップ4では決定をゼロから再構成するのではなく、この行群を核に文書を組み立てる。

## ステップ3 — 未決定事項

予算が尽きた時点で残っている質問(またはユーザーが明示的に保留とした質問)はすべて未決定事項セクションに入れる。各項目には次を含める: 質問内容、検討した選択肢、**根拠付きの推奨仮回答**、その推奨が外れた場合の影響・リスク — これにより、設計フェーズは記載された仮定のもとで前進でき、止まらずに済む。回答の決定権がインタビュー対象者以外にある場合(法務、営業部長、外部ベンダーなど — 典型的にはユーザーが「わからない」「要確認」と答えた場合)は、確認先(誰・どの部署が解決すべきか)も記録する。仮の回答を、あたかも決定済みであるかのように文書本文に黙って組み込んではならない。

## ステップ4 — 文書を書く

出力先: `<project_root>/docs/requirements/<feature-slug>.md`。`<feature-slug>` はその機能を表す短いケバブケースの英語スラッグ(例: `avatar-upload.md`、`csv-export.md`)。必要に応じて親ディレクトリを作成する。書き込んだファイル名を明示する。曖昧な場合のみ確認のために尋ねる。

**更新モード:** インタビュー開始前からファイルが存在していた場合(ステップ2で自分が追記した決定記録の下書きは含まない)、無条件に上書きしない。まず読み込むこと。もし別の機能について書かれたものがたまたま同じスラッグを共有しているなら、別のスラッグを選ぶ。もし同じ機能の以前のバージョンであれば、その旨をユーザーに伝え、新しい情報を既存文書に統合する — 該当する未決定事項を解消し、影響を受けるセクションを更新し、決定記録に追記する。要件定義書は書き直すのではなく改訂する。

文書本文は特に指示がない限り日本語で書く。以下の構成をそのまま使用する — 書くことがないセクションは削除せず「なし」とする。これにより後続フェーズがこの形を前提にできる。

```markdown
# <機能名>

## 概要
<何を作るか、1段落>

## 背景・目的
<なぜ作るか。ビジネス上の狙い>

## スコープ
<作る/直すものの具体的な箇条書き>

## 対象外(Non-goals)
<今回は明示的にやらないこと>

## 影響範囲
<この機能が触れるレイヤーを対象プロジェクトの構成に即して具体的に(例: 画面コンポーネント / フロント状態管理 / APIクライアント / バックエンドAPI / サービスロジック / DBスキーマ)。設計・テストフェーズが何に手を入れるかの判断に使う>

## 機能要件
- FR-1: <検証可能な粒度の要件>
- FR-2: …

## 画面・UIフロー
<関係する画面と遷移。既存画面への追加なら既存構造に言及>

## 受け入れ基準
- AC-1: <条件>(検証方法: 自動テスト / 手動確認)
- AC-2: …

## 制約
<既存アーキテクチャ・ライブラリ・規約のうち設計が従うべきもの(ステップ1の調査結果)>

### 前提(調査により確認)
<質問の代わりにステップ1の調査で仮確定した判断の一覧。誤った推測をユーザーがレビュー時に否認できるよう明示する。なければ「なし」>

## 重大な非機能要件
<仕様に影響する項目のみ。なければ「なし」>

## 未決定事項
- <質問> — 選択肢: <A / B> / 推奨仮置き: <A>(<根拠>)/ 外れた場合の影響: <…> / 確認先: <誰・どの部署>(決定権が回答者以外にある場合のみ)

## 決定記録
- Q1: <質問> → <選ばれた選択肢>(理由: <…>)

## 用語集
<ビジネス用語 ↔ システム上の概念の対応。齟齬が出やすい語のみ>
```

セクション別の補足:

- **FR / AC の ID は安定参照** — 後続フェーズ(設計、テスト、レビュー)がこれらを参照するため、更新時に既存のIDを振り直さないこと。
- **受け入れ基準** — すべてのFRは少なくとも1つのACでカバーされること。ACのないFRは誰も検証しない要件になる。否定形のFR(「〜しない」「上限を設けない」)も対象 — その挙動が存在しないままであることを確認するACを書く。ハッピーパスだけでなく主要な異常系もカバーする。可能な限り機械的に検証可能な条件を優先し、それぞれに自動テスト または 手動確認 のタグを付けてテスト工数を事前に可視化する。このフォーマットは dev-pipeline の requirements-analyst の出力と互換性があり、そのまま `/dev-pipeline` に渡せる。
- **決定記録** — 回答された質問ごとに1行(ステップ2で逐次追記済み)。推奨のデフォルトがそのまま採用された場合も含む。これにより半年後の設計者が仕様の理由を理解できる。

## まとめ

最終メッセージには次を含める: 書き込んだファイルパス、30問中の使用数、未決定事項とその推奨仮回答の一覧(あれば)— ユーザーがファイルを開かなくても行動できるように。ユーザーが修正や異議を返信してきた場合は、更新モードで取り込む — インタビューを最初からやり直さない。

一貫して簡潔であること。読むのに10分かかる要件定義書は、2分で読める文書より劣る。
