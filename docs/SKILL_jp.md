# refine-requirements

事業責任者が書いた粗い要件 — 典型的には不完全・曖昧でビジネス用語で書かれている — を受け取り、設計者が推測に頼らず設計フェーズへ渡せるほど精緻な要件定義書に変換する。リポジトリの調査、選択式質問によるユーザーへのインタビュー、文書の作成、という3フェーズで進める。

解決策の設計やコードの記述は行わない。要件定義書が成果物のすべてである。

## 入力

粗い要件はチャットのテキスト、またはファイルへのパス（.md / .txt — 読み込むこと）として渡される。どちらもない場合は、作業を始める前に要件を尋ねること。入力に複数の独立した機能が混在している場合は、機能ごとに1文書ずつ分割することを提案し（出力の慣例は1機能1ファイル）、インタビューを始める前にユーザーに選んでもらう。

## ステップ1 — 質問する前に調査する

自分で答えられる質問は絶対に尋ねない。インタビューの前に対象プロジェクト（特に指定がなければカレントディレクトリ）を調査する: 規約や過去の意思決定は `README` と `docs/`（特に `docs/pipeline-config.md` と既存の `docs/requirements/*.md`）、そして機能が触れるコード領域 — 類似の既存機能、画面・ルーティング構造、APIパターン、データモデル。推奨の根拠を示せる状態になった時点で調査は完了 — リポジトリ全体の理解が目的ではない。読み取り専用の探索サブエージェント（Explore など）への委譲は、大規模コードベースの本当に広範な調査に限り（要約だけをコンテキストに残す）、少数の絞り込み検索で足りる場合は自分で行う。

質問する代わりに調査から解決した曖昧点は、ユーザーの意思決定ではなく推論である: 制約セクションの前提リストに集約し、ユーザーが文書レビュー時に誤った推測を否認できるようにする。調査で解決できなかったものがインタビューの材料になる。

## ステップ2 — インタビューのループ

一度のパスで、作られるものを実質的に左右するすべての曖昧点を洗い出す — 機能面と非機能面をまとめて。非機能面の発見（コンプライアンス、データの機微性）が後から出てくると、すでに下した機能面の判断を覆しかねないため。

- **機能面の曖昧点**（主題）: 挙動、画面、データ、エッジケース、権限としての振る舞い。
- **仕様を実質的に左右し得る非機能面の曖昧点**: 認証・認可モデル、個人情報や機微データの扱い、設計を左右する規模のデータ量・パフォーマンス、外部連携の可用性、法務・コンプライアンス上の制約。ありきたりな非機能要件（一般的な性能要望、ロギングの慣例）はリストに含めない。

洗い出しの際は、要件定義でありがちな見落としのチェックリストを確認する。これが統制するのは洗い出しのみ — 質問にするかどうかは以下のインパクト順序と予算に従い、この機能に明らかに無関係な項目はスキップする:

- アクターと権限: 誰が使うか、ロールによって挙動が変わるか
- 異常系・エッジケース: 入力不正 / 0件 / 上限超過 / 外部サービス障害時の挙動
- データ: 入出力の形式、保持期間、既存データの移行の要否
- スコープ境界: メモに書かれていないが隣接する機能を、やるのか・やらないのか
- 同時実行・競合、通知・監査ログの要否

リストはインパクト順に並べる: 仕様を大きく左右する回答を持つ質問を先に。予算を最も重要な箇所に使うためである。

**予算: 30問 — ハードキャップであり、目標ではない。** 典型的なメモは3〜4ラウンド・8〜15問で収束する。実際に提示したすべての選択式質問がカウント対象であり、フォローアップも含む。入力メモを尋ねること、機能分割の提案、ファイル名の確認はカウントしない。各ラウンドの質問の前に累計数を明示する（例: `質問 5–8 / 30`）。実質的な曖昧点が残っていなければその時点で打ち切り、予算が尽きた時点で残っている項目はすべて未決定事項になる（ステップ3）。

質問は1ラウンドあたり最大4問の関連する質問をまとめて提示する。各質問は以下を満たす。

- 2〜4個の具体的な選択肢。可能な限り互いに排他的にする。
- 推奨する選択肢には「（推奨）」と一行の根拠を付ける。根拠は必ず次のいずれかに紐付け、どれに基づくかを明示する: 明示されたビジネス上の目的、UI/UX、実装難易度、リポジトリの現行設計。根拠が現行設計の場合は、ステップ1で見つけたファイルやディレクトリ（例: `src/features/export/`）を引用し、主張を検証可能にする。根拠付けできない推奨には印を付けない。
- 環境に `AskUserQuestion` ツールがあれば使用する（推奨の選択肢を先頭に、「（推奨）」と表示）。それ以外 — 例: GitHub Copilot — の場合は、選択肢を番号付きリストとしてチャットに提示し、回答を待つ。選択肢にない自由記述の回答は常に有効であり、そのまま取り込む。

ある回答が粗いメモや以前の回答と矛盾する場合は、その矛盾を指摘し、どちらを優先するか確認してから取り込む（この確認もカウント対象）。

各ラウンドが終わるたび、次のラウンドを提示する前に、回答1件につき決定記録1行を出力ファイル（ステップ4のパス — スラッグは最初のラウンドで確定する。ファイルが既に存在していた場合は更新モード〔ステップ4〕であり、そのファイルに追記する）へ追記する。長いインタビューはコンテキストウィンドウより長生きし得る: 恒久的な記録は会話の記憶ではなくファイルであり、ステップ4はこの行群を核に文書を組み立てる。

## ステップ3 — 未決定事項

予算が尽きた時点で残っている質問、またはユーザーが明示的に保留とした質問は、テンプレートが示す書式で未決定事項セクションに入れる: 検討した選択肢、根拠付きの推奨仮回答、外れた場合の影響 — これにより設計フェーズは記載された仮定のもとで止まらず前進できる。決定権がインタビュー対象者以外にある場合（法務、営業部長、外部ベンダーなど — 典型的には「わからない」「要確認」という回答）は、確認先も記録する。仮の回答を、あたかも決定済みであるかのように文書本文に黙って組み込んではならない。

## ステップ4 — 文書を書く

出力先: `<project_root>/docs/requirements/<feature-slug>.md`。`<feature-slug>` はその機能を表す短いケバブケースの英語スラッグ（例: `avatar-upload.md`、`csv-export.md`）。必要に応じて親ディレクトリを作成する。書き込んだファイル名を明示し、本当に曖昧な場合のみ尋ねる。

**更新モード:** インタビュー開始前からファイルが存在していた場合（ステップ2で自分が追記した決定記録の下書きは含まない）、まず読み込むこと。別の機能がたまたま同じスラッグを共有しているなら、別のスラッグを選ぶ。同じ機能の以前のバージョンであれば、その旨をユーザーに伝えて改訂する — 新しい回答で解消できる未決定事項を解消し、影響を受けるセクションを更新し、決定記録に追記する。要件定義書は書き直すのではなく改訂するものであり、既存の FR / AC の ID は決して振り直さない: 後続フェーズ（設計、テスト、レビュー）がこれらを参照するためである。

文書本文は特に指示がない限り日本語で、以下の構成をそのまま使用して書く — 書くことがないセクションは削除せず「なし」とする。これにより後続フェーズがこの形を前提にできる。

```markdown
# <機能名>

## 概要
<何を作るか、1段落>

## 背景・目的
<なぜ作るか。ビジネス上の狙い>

## スコープ
<作る/直すものの具体的な箇条書き>

## 対象外（Non-goals）
<今回は明示的にやらないこと>

## 影響範囲
<この機能が触れるレイヤーを対象プロジェクトの構成に即して具体的に（例: 画面コンポーネント / フロント状態管理 / APIクライアント / バックエンドAPI / サービスロジック / DBスキーマ）。設計・テストフェーズが何に手を入れるかの判断に使う>

## 機能要件
- FR-1: <検証可能な粒度の要件>
- FR-2: …

## 画面・UIフロー
<関係する画面と遷移。既存画面への追加なら既存構造に言及>

## 受け入れ基準
<全 FR を少なくとも1つの AC でカバーする。否定形の FR（「〜しない」「上限を設けない」）にも、その挙動が現れないことを確認する AC を書く。主要な異常系を含め、機械的に検証可能な条件を優先する>
- AC-1: <条件>（検証方法: 自動テスト / 手動確認）
- AC-2: …

## 制約
<既存アーキテクチャ・ライブラリ・規約のうち設計が従うべきもの（Step 1 の調査結果）>

### 前提（調査により確認）
<質問の代わりに Step 1 の調査で仮確定した判断の一覧。誤った推測をユーザーがレビュー時に否認できるよう明示する。なければ「なし」>

## 重大な非機能要件
<仕様に影響する項目のみ。なければ「なし」>

## 未決定事項
- <質問> — 選択肢: <A / B> / 推奨仮置き: <A>（<根拠>）/ 外れた場合の影響: <…> / 確認先: <誰・どの部署>（決定権が回答者以外にある場合のみ）

## 決定記録
<回答された質問ごとに1行（Step 2 で逐次追記済み）。推奨案がそのまま採用された場合も含む — 半年後の設計者が仕様の理由を辿れるように>
- Q1: <質問> → <選ばれた選択肢>（理由: <…>）

## 用語集
<ビジネス用語 ↔ システム上の概念の対応。齟齬が出やすい語のみ>
```

AC-ID・検証方法タグの書式は dev-pipeline の requirements-analyst の出力と互換であり、文書はそのまま `/dev-pipeline` に入力できる。

## まとめ

最終メッセージには次を含める: 書き込んだファイルパス、30問中の使用数、未決定事項とその推奨仮回答の一覧 — ユーザーがファイルを開かなくても行動できるように。ユーザーが修正や異議を返信してきた場合は、更新モードで取り込む — インタビューを最初からやり直さない。

文書は機能が必要とする分量に合わせる: 実質を漏らさず書き、埋め草のセクション・定型文・文脈の繰り返しで水増ししない。
